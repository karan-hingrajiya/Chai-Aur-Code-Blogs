## Introduction

When you start learning software development, one of the first tools you hear about is **Git**.  
Most beginners learn a few commands and start using Git without fully understanding **what Git actually is**, **why it exists**, and **how it works internally**.

This article is written for **absolute beginners**. We will start from the very basics—what Git is and why it is used—and then move step by step toward core concepts, common commands, and a simple real-world developer workflow. By the end, you will have a **clear mental model of Git**, not just command memorization.

## What Is Git?

**Git** is a **distributed version control system**.

In simple words:

> **Git is a tool that tracks changes in your files over time.**

Git is a **software tool** that:

* tracks changes in files
    
* stores a history of those changes
    
* allows developers to compare different versions of the same code
    

It continuously monitors the project and records updates in the `.git` folder. This makes Git a **reliable and automatic code tracker**, eliminating the need for manual comparisons or guesswork.

Git keeps a record of:

* what changed
    
* when it changed
    
* and how the code looked at every point in time
    

This makes it possible to safely modify code, experiment freely, and recover older versions whenever needed.

---

## Why Git Is Used

Before Git, developers had major problems while working on projects:

* files were copied manually
    
* changes were overwritten
    
* collaboration was slow and risky
    
* tracking history was almost impossible
    

Git was created to solve these problems.

### Git helps developers to:

* track changes in code
    
* work without fear of losing previous versions
    

## Git Basics and Core Terminologies

Before using Git commands, it is important to understand a few **core concepts**.

---

### 1 .Repository (Repo)

A **repository** is a project folder that Git is tracking.

* It contains your project files
    
* It also contains a hidden `.git` folder
    
* The `.git` folder stores the entire history of the project or you can say its keep track of your code history that tracking by git.
    

Once a folder becomes a Git repository, Git starts monitoring it.

---

### 2 . Commit

A **commit** is a snapshot of your project at a specific point in time.

Think of it as:

* “I want to save the current state of my project”
    

Each commit:

* has a unique ID
    
* stores changes, not entire files
    
* includes a message describing what was changed
    

---

### 3 . Branch

A **branch** is an independent line of development.

* The default branch is usually called `main`
    
* Branches allow you to work on features without affecting the main code
    
* Later, branches can be merged together
    

Branches make parallel development possible.

---

### 4 . HEAD

**HEAD** is a pointer that shows:

* where you are currently working
    
* which commit is active
    

When you move between branches or commits, HEAD moves accordingly.

## Git Working Areas (Very Important Concept)

Git internally works with **three main areas**:

1. **Working Directory** – where you write and edit files
    
2. **Staging Area** – where you prepare changes before saving
    
3. **Repository** – where commits are stored permanently
    

This separation gives Git precise control over what gets saved and when.

## Common Git Commands (Beginner-Friendly)

To truly understand Git, we should not just memorize commands—we should **see how Git behaves** when files change.

In this section, we will use **one file (**`t1.txt`) and walk through:

* `git init`
    
* `git status`
    
* `git add`
    
* `git commit`
    
* `git log`
    

We will also see **how Git history looks internally**.

---

## Step 0: Initialize a Git Repository

First, create a folder and initialize Git.

```bash

git init
```

### What Git Does Internally

* Creates a hidden `.git` folder
    
* This folder will store **entire history** of the project
    
* git init means telling the git to now start tracking the code remember we have to initialize git one time so we write first this command to track our code file.
    

At this point, **no files are tracked yet** just git is initialized.

## Step 1: Create a File (`t1.txt`)

Create a file:

```bash
t1.txt
```

Add some content:

```bash
Hello Git
```

Now check Git status:

```bash
git status
```

### Output (Conceptual)

```bash
Untracked files:
  t1.txt
```

### Meaning

* Git sees the file
    
* But Git is **not tracking it yet we are just checking our files status here our files is untracked yet means git is not tracking our code or file yet in order to do that we do this :**
    

## Step 2: Stage the File (`git add`)

Now tell Git that you want to track this file.

```bash
git add t1.txt
```

Check status again:

```bash
git status
```

### Output

```bash
Changes to be committed:
  new file: t1.txt
```

### What Happened Internally

* File moved from **working directory** → **staging area**
    
* now our files is going to staging area which is term given by git when git not tracking file it called untracked and when we write git add means now git is tracking the code but hasn’t saved yet.
    
* it means that Git prepared a snapshot of our entire file content but hasn’t saved it yet.
    

## Step 3: Commit the File (`git commit`)

Now permanently save this version.

```bash
git commit -m "Adding something"
```

### Output

```bash
[main a1b2c3d] Add t1.txt with initial content
 1 file changed, 1 insertion(+)
```

### What Git Did

* Created a **commit (node)** in history
    
* Stored snapshot of `t1.txt`
    
* in here with commit or making changes we write some message along with commit that what we are changing in our file.
    

## Git History After First Commit

```bash
A (HEAD)
```

Where:

* `A` = first commit
    
* `t1.txt` contains: `Hello Git`
    

---

## Step 4: Modify the File

Edit `t1.txt`:

```bash
Hello Git
Learning Git step by step
```

Check status:

```bash
git status
```

### Output

```bash

```

Git detects the change but has **not saved it yet**.so here comes one more term called modified means when the git is tracking existing file and we commit one time or more time and then we again do some changes in our file which is tracking by git then git shows status modified.

## Step 5: Stage the Changes Again

```bash
git add t1.txt
```

Now commit:

```bash
git commit -m "Update t1.txt with learning message"
```

### Output

```bash
[main d4e5f6g] Update t1.txt with learning message
 1 file changed, 1 insertion(+)
```

---

## Git History Now Looks Like This

```bash
A --- B (HEAD)
```

* `A` → initial version of `t1.txt`
    
* `B` → updated version
    
* Each commit is a **node**
    
* Each node points to the previous one
    

---

## Step 6: View Commit History (`git log`)

```bash
git log
```

### Output (Simplified)

```bash

Message: Update t1.txt with learning message

commit a1b2c3d
Author: Karan
Message: Add t1.txt with initial content
```

### What This Shows

* Latest commit on top
    
* Older commits below
    
* Each commit has:
    
    * unique hash
        
    * message
        
    * snapshot reference
        

## Shorter History View (`git log --oneline`)

```bash
git log --oneline
```

### Output

```bash
d4e5f6g Update t1.txt with learning message
a1b2c3d Add t1.txt with initial content
```

This is how developers usually view history.

## Git History as Nodes (Mental Model)

```bash

   ↑
Commit A
```

* Each commit = node
    
* HEAD points to the current commit
    
* Git moves HEAD as commits are added

## Revert and Reset Commands Essential for revert changes

Let’s assume this is your project history:

```bash
A --- B --- C --- D (HEAD)
```

* `A` → Initial project setup
    
* `B` → Added login feature
    
* `C` → Added payment gateway
    
* `D` → Buggy change (problematic commit)
    

Now you realize commit `D` introduced a serious bug.

## What Is `git revert`?

### Definition (Simple)

> `git revert` creates a new commit that undoes a previous commit.

Important:

* It does **NOT delete history**
    
* It **adds a new commit**
    
* Safe for shared projects
    

---

## `git revert` with Example

Let’s say commit `D` is buggy.

## `git revert` with Example

Let’s say commit `D` is buggy.

### Step 1: View history

```bash
git log --oneline
```

Output:

```bash
d4f3a2d  Buggy feature
c3b2a1c  Added payment gateway
b2a1c0b  Added login
a1b0c9d  Initial commit
```

### Step 2: Revert the bad commit

```bash
git revert d4f3a2d
```

Git will:

* create a **new commit**
    
* reverse the changes from `d4f3a2d`
    

### New History

```bash
A --- B --- C --- D --- E (HEAD)
```

Where:

* `E` = “Revert ‘Buggy feature’”
    
* History is **preserved**
    
* Team members stay in sync
    
* This is why `git revert` is preferred in collaboration.
    

## When Should You Use `git revert`?

Use `git revert` when:

* you already pushed code to GitHub
    
* others are working on the same branch
    
* you want a **safe undo**
    

---

## What Is `git reset --hard`?

### Definition (Simple)

> `git reset --hard` moves HEAD to an older commit and deletes all changes after it.

⚠️ WARNING:

* It **rewrites history**
    
* Deleted commits are lost (unless recovered)
    
* Dangerous in shared repositories
    

---

## `git reset --hard` with Example

Using the same history:

```bash
A --- B --- C --- D (HEAD)
```

Suppose you want to completely remove commit `D`.

### Step 1: Reset to commit `C`

```bash
git reset --hard c3b2a1c
```

### New History

```bash
A --- B --- C (HEAD)
```

* Commit `D` is **gone**
    
* Working directory is reset
    
* Staging area is reset
    
* It’s like commit `D` **never existed**
    

## When Should You Use `git reset --hard`?

Use it when:

* you are working **alone**
    
* changes are **not pushed**
    
* you want to clean local mistakes
    

❌ Avoid using it on shared branches.
